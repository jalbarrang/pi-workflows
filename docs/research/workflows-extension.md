# Research: Workflows Extension → Publishable Pi Package (Effect v4, DDD, sub-100-line files)

Scope: port of the upstream `workflows` extension (`/tmp/pi-workflows-upstream/extensions/workflows`, from https://github.com/davis7dotsh/my-pi-setup, commit `21f40f4`, pi 0.82) into a publishable pi package modeled on `/Users/jalbarran/fun/drekki/pi-plan-mode`. Research only — no implementation here.

## 1. Observed behavior and user-facing workflow

- The extension registers one LLM tool, `workflow` (`index.ts:339`), and one command, `/workflows` (`index.ts:290`). The tool's description gates use: "only to be called when the user says 'ultracode' or specifically requests a workflow run" (`prompt.ts:20`).
- The model writes an inline JavaScript orchestration script. It may start with `export const meta = { name, description, phases: [{ title, detail? }] }` (statically parsed via acorn, never evaluated — `meta.ts:206-247`), then uses four sandbox globals: `phase(title)`, `await agent(prompt, { label?, phase?, schema?, model?, provider?, effort? })`, `await parallel([thunks], { concurrency? })`, and `args` (parsed JSON from the `args` tool parameter). The script `return`s a JSON-serializable aggregate.
- `agent()` never throws into the script; it always resolves `{ ok, output, structured?, error? }` and scripts branch on `ok` (`index.ts:14-16`, `prompt.ts:24`). Passing a JSON `schema` injects a one-shot terminating `structured_output` tool into the child and fails the agent if it never calls it (`runner.ts:180-201`, `runner.ts:531-543`).
- Each `agent()` call becomes an isolated in-process `AgentSession` (`createAgentSession` + `SessionManager.inMemory`, `runner.ts:381-395`): normal built-ins, trust-gated extensions/skills/AGENTS.md via a fresh `DefaultResourceLoader` per child (`shared/child-session.ts:38-52`), but recursive orchestration and `ask_user` denied via `excludeTools` (`shared/child-session.ts:15-28`).
- Runs are blocking by default with throttled live tool-block updates (120 ms, `index.ts:87`); `background: true` returns a launch message immediately and delivers the settled result later via `pi.sendUserMessage(..., { deliverAs: "followUp" })` (`index.ts:645-668`). A footer status indicator tracks running/done/failed counts (`index.ts:229-253`).
- Budgets and deadlines: max 32 agent calls per run (`controller.ts:2`), global concurrency cap 4 (`controller.ts:1`), 45 s first-assistant-response watchdog per agent (`runner.ts:44`), 3 min per child tool call (`shared/tool-call-timeout.ts:3`), 8 s settle deadline at run teardown (`controller.ts:3`), no overall run deadline, no resume (failed runs are re-run).
- Artifacts persist under `~/.pi/agent/workflows/<runId>/`: `script.js`, `args.json`, `workflow.json` (compact details), `result.json`, `transcripts.json` (bounded per-agent transcripts), checkpointed every 500 ms with atomic same-directory renames (`artifacts.ts:11,96-131`, `serialization.ts:157-171`).
- `/workflows` opens a full-screen TUI dashboard (run list → per-run detail with phases sidebar, agents panel, transcript viewer, "s" saves a report — `dashboard.ts:1-12`); non-TUI mode falls back to a plain-text listing/select (`index.ts:301-330`). Only runs from the current session or referenced by its tool results are listed (`index.ts:186`, `dashboard.ts:211-228`).
- Rendering: `renderCall` shows name/description/phases parsed from partial script text; `renderResult` shows a collapsed status header per agent and an expanded phase-grouped view with usage totals and result JSON (`index.ts:696-871`).

## 2. Sandbox security model (exact observed mechanics)

- Orchestration source runs in a separate Node child spawned with `--permission --allow-fs-read=<worker dir only> --max-old-space-size=128 --stack-size=2048`, env limited to `PATH` + `NODE_NO_WARNINGS`, stdio ignored except an IPC channel (`sandbox.ts:106-125`). The host refuses to run if the runtime lacks `--permission` support (`sandbox.ts:89-93`).
- The child compiles the script in a `vm` context with `codeGeneration: { strings: false, wasm: false }`, strips `process` capabilities (`getBuiltinModule`, `binding`, `dlopen`, `kill`, `send`, …) up front, and exposes only frozen `agent/parallel/phase/args` bridges (`sandbox-child.cjs:6-31,215-224`). A bootstrap thenable defers each `agent()` request until awaited and fails runs that finish with unawaited or in-flight agent calls (`sandbox-child.cjs:47-90,241-252`).
- All IPC is token-authenticated and size/count-bounded: source ≤512 KB, args ≤256 KB, result ≤1 MB, agent messages ≤512 KB, ≤32 agent requests, prompts ≤100 k chars; violations kill the run (`sandbox.ts:7-11,169-260`). `meta.ts` fails closed on any non-literal metadata and blanks the meta declaration while preserving line numbers (`meta.ts:70-118,231-247`).

## 3. Domain glossary

- **Workflow script**: model-authored async JS body; the only untrusted code. **Meta**: statically-extracted name/description/declared phases. **Run**: one execution (`wf_<hex>` id) with status running|completed|failed|aborted. **Phase**: named stage grouping agents for progress display. **Agent call / AgentRecord**: one isolated child session invocation with label, phase, state (running|done|error), usage, preview, transcript. **Structured output**: schema-validated terminating tool result. **RunController**: run-scoped fanout budget + abort tree + settle barrier. **Sandbox**: permission-restricted child process executing the script. **Artifact**: persisted run files under the run dir. **Dashboard**: `/workflows` TUI overlay. **Background run**: run detached from the parent turn, settled via follow-up message. **Watchdog**: first-response timeout. **Transcript**: bounded serializable child conversation.

## 4. Bounded contexts / module proposal (DDD)

- **Scripting** (pure domain): parse/validate scripts, extract meta, prepare source. No IO. Upstream: `meta.ts`.
- **Sandboxing** (infrastructure): child-process lifecycle + authenticated IPC protocol. Ports: `onAgent`, `onPhase`. Upstream: `sandbox.ts`, `sandbox-child.cjs` (the `.cjs` worker stays plain Node — it must run standalone under `--permission`).
- **Agent execution** (domain + infra adapter): child session creation, tool policy, structured output, watchdog, transcript/usage projection. Upstream: `runner.ts`, `shared/child-session.ts`, `shared/tool-call-timeout.ts`.
- **Run orchestration** (application core): run aggregate (`WorkflowDetails`), scheduling/budget/abort/settle, model+effort resolution, progress events. Upstream: `controller.ts` + the ~450-line `execute` closure in `index.ts`.
- **Artifacts** (infrastructure): bounded serialization, atomic writes, throttled checkpoints, run-dir reads for listing. Upstream: `artifacts.ts`, `serialization.ts`, parts of `index.ts:154-210`.
- **Presentation** (interface): tool/result renderers, dashboard, status indicator, prompt/description text. Upstream: `model.ts` formatters, `dashboard.ts`, `prompt.ts`, render fns in `index.ts`.
- **Shared kernel**: `WorkflowDetails`, `AgentRecord`, `AgentUsage`, `TranscriptEntry`, status enums (upstream `model.ts:18-100`). Keep types separate from formatting helpers (upstream mixes both).

## 5. Upstream strengths (preserve)

- Defense-in-depth sandbox (permission mode + vm + capability stripping + bounded authenticated IPC) with explicit fail-closed behavior everywhere; excellent threat-model comments (`sandbox-child.cjs:3-11`).
- `agent()`-never-throws contract keeps model-authored scripts simple and robust; unawaited-call detection catches a real LLM authoring bug class.
- Bounded everything: bytes, depth, nodes, entries, calls, concurrency, timeouts — no unbounded memory or artifact growth.
- Strong test seams already exist: `RunController`, watchdog, transcript projection, persistence throttling, sandbox protocol are all tested pure or with fakes (23 tests across 6 files, `node --test --experimental-strip-types`).
- Honest failure semantics: tool failure = throw (pi ignores `isError`, noted at `index.ts:679-681`); orphaned agents get explicit error states at settle.

## 6. Upstream risks / gaps

- `index.ts` (871 lines) and `dashboard.ts` (1063 lines) concentrate orchestration, state mutation, rendering, and IO; the `execute` closure mutates shared `details` from many async callbacks — the main port hazard and the motivation for Effect-managed state.
- Hand-rolled concurrency plumbing (Semaphore, abort-listener bookkeeping, settle races, watchdogs, throttles) is exactly what Effect replaces with `Semaphore`, `Scope`, `Effect.timeout`, `Effect.race`, and interruption — but semantics must be preserved test-for-test (e.g. invocation-abort does not abort the run, `controller.test.ts`).
- Depends on internal pi surfaces: `session.extensionRunner` (child shutdown), `msg.responseModel`, `truncateHead`, `formatActivityStatus`; pin `@earendil-works/pi-*` versions and isolate these behind adapters. Upstream targets pi ^0.82.0 while pi-plan-mode devDeps are ^0.80.10 — verify against the version you pin.
- Node `--permission` requirement (Node ≥20 experimental / ≥22 stable surface) is a hard runtime constraint worth documenting in the README; the extension errors at run time otherwise (`sandbox.ts:89-93`).
- `shared/` helpers are imported from a sibling directory (`../shared/*`); a package must vendor them under its own extension dir (pi packages ship whole directories; see pi-plan-mode `files` whitelist).
- Minor: meta cache clears wholesale at 32 entries; `listRuns` reads every run dir synchronously on command; dashboard state is untested.

## 7. Effect v4 — version evidence and API mapping

- Versions (npm view, observed during this research): `effect` dist-tags `latest: 3.22.0`, `beta: 4.0.0-beta.101`. v4 lives in https://github.com/Effect-TS/effect-smol; the beta announcement (https://effect.website/blog/releases/effect/40-beta/) states betas "may include breaking changes" and recommends v3 for production. **Recommendation: pin an exact beta (`"effect": "4.0.0-beta.101"`), no caret**, and gate upgrades on CI.
- v4 consolidates platform/rpc/cluster into `effect` with subpath exports (`effect/*`, `effect/unstable/*`, `effect/testing` — confirmed in the published package `exports` map). Core model (Effect, Layer, Schema, Stream) is unchanged from v3 (MIGRATION.md).
- Services: `Context.Service<Self, Shape>()("Id")` replaces `Context.Tag`/`Effect.Tag`/`Effect.Service`; no auto `.Default` layer — define `static layer = Layer.effect(this, make)` and wire deps via `Layer.provide`; v4 convention names layers `layer`/`layerTest` (https://github.com/Effect-TS/effect-smol/blob/main/migration/services.md). Note: mid-beta, `ServiceMap` was renamed back to `Context` (https://effect.website/blog/effect-v4beta-launch-to-may-recap/), an example of beta churn.
- Mapping upstream mechanics → Effect v4: Semaphore+queue → `Effect.makeSemaphore(4).withPermits(1)` or `Effect.forEach(..., { concurrency: 4 })`; RunController abort tree → fiber interruption + `Scope` (`Effect.acquireRelease` for child sessions and the sandbox process); settle deadline → `Effect.timeout` on `Fiber.awaitAll`; first-response watchdog → `Effect.race`/`Effect.timeoutFail` armed until a `Deferred` fires; checkpoint throttle → a scoped repeating fiber (`Effect.schedule`) over a `Ref`-held dirty flag; run state mutation → `Ref<WorkflowDetails>` (or `SubscriptionRef`) instead of shared mutable object; typed failures → `Data.TaggedError` per context (ScriptParseError, SandboxProtocolError, AgentFailure, PersistenceError); artifact/IPC payload validation → `effect/Schema` (stable in v4). Note `effect/unstable/workflow` exists but is durable-execution-oriented and unstable — not a fit; build on stable core modules only.
- Boundary rule: pi's extension API is Promise-based, so run Effect programs at the edges via `Effect.runPromise`/`Effect.runFork` with an `AbortSignal` bridge (pi `signal` → fiber interruption); keep `sandbox-child.cjs` Effect-free.

## 8. Pi extension/package constraints (from local docs)

- Package manifest: `package.json` `pi.extensions`/`pi.skills` arrays + `pi-package` keyword; convention dirs work without a manifest (`/Users/jalbarran/.bun/install/global/node_modules/@earendil-works/pi-coding-agent/docs/packages.md`, "Creating a Pi Package").
- Dependencies: runtime deps in `dependencies` (pi runs `npm install --omit=dev` on install, so devDeps are unavailable at runtime — extensions.md:145); pi-bundled packages (`@earendil-works/pi-ai`, `pi-coding-agent`, `pi-tui`, `typebox`) go in `peerDependencies` with `"*"` and must not be bundled (packages.md, "Dependencies"). `effect` and `acorn` are therefore regular `dependencies`.
- Extensions load via jiti — TypeScript ships as source, no build step (extensions.md:158). Entry is a default factory receiving `ExtensionAPI`; don't start background resources in the factory; register idempotent `session_shutdown` cleanup (extensions.md, "Long-lived resources and shutdown") — upstream already conforms (`index.ts:258-282`).
- Tool registration: `promptSnippet` opts into the Available-tools list; `promptGuidelines` bullets must name the tool explicitly (extensions.md:1343-1345). `pi.sendUserMessage` requires `deliverAs` while streaming (extensions.md:1429-1433). `pi.getThinkingLevel()` returns the 7-level enum upstream mirrors (extensions.md:1663-1668).
- SDK for children: `createAgentSession` + `SessionManager.inMemory()` + custom `DefaultResourceLoader`/`SettingsManager`, `excludeTools` after allowlist (sdk.md:19-62,499). Template precedent: pi-plan-mode declares the same peer/dev split, `files` whitelist excluding `__tests__`, `publishConfig.access: public` (`/Users/jalbarran/fun/drekki/pi-plan-mode/package.json`).

## 9. Recommended architecture (sub-100-line files)

- Layout: `extensions/workflows/index.ts` (thin composition root: build layers, register tool + command, ≤100 lines) over `extensions/workflows/{scripting,sandbox,agent,run,artifacts,present}/` modules, each file one concept ≤100 physical lines; `__tests__/` mirrors the tree. Worst offenders split as: upstream `index.ts` → `tool-definition.ts` (params + descriptions ref), `execute.ts` (run use-case), `agent-call.ts` (script→agent adapter), `run-registry.ts` (active runs + indicator), `render-call.ts`, `render-result.ts`; upstream `dashboard.ts` → `state.ts`, `run-list.ts`, `detail-view.ts`, `transcript-view.ts`, `report.ts`, `keys.ts`; upstream `runner.ts` → `session.ts`, `structured-output.ts`, `watchdog.ts`, `transcript.ts`, `usage.ts`, `outcome.ts`.
- Each bounded context exposes a `Context.Service` (e.g. `SandboxRunner`, `AgentRunner`, `ArtifactStore`, `Clock`-like `RunIds`) with a production `layer` and a test layer; pi/SDK objects (`ExtensionContext`, model registry, UI) are passed at the edge, never imported deep in the domain.
- Keep upstream limits as named constants in one `limits.ts` per context; keep `sandbox-child.cjs` byte-compatible with upstream (it is security-reviewed logic; 274 lines is acceptable as a documented exemption or split into `bootstrap` string + host shim if the 100-line rule must hold — "where practical" applies).

## 10. Tooling: line limit, lint, format

- ESLint (flat config, `eslint.config.js`, ESLint ^10): enable only `max-lines: ["error", { max: 100, skipBlankLines: false, skipComments: false }]` (physical lines; rule docs https://eslint.org/docs/latest/rules/max-lines) over `extensions/**/*.ts`, with an explicit `ignores` for generated files and any documented exemptions (`sandbox-child.cjs` if kept whole). Keep oxlint (template parity, `oxlint extensions`) for general correctness lint; ESLint exists solely to enforce the line budget oxlint does not cover.
- oxfmt (^0.60): agent-safe config in `.oxfmtrc.json` — `{ "proseWrap": "preserve" }` is already the default (markdown prose is never re-wrapped: https://oxc.rs/docs/guide/usage/formatter/config-file-reference.html#prosewrap), so the no-hard-wrap rule holds by default; set `printWidth: 100`, do not enable `jsdoc` formatting (its `greedy` wrapping re-wraps comment prose, breaking exact-text edit tooling), and scope scripts to code dirs (`oxfmt --write extensions bin`) as pi-plan-mode does. Never set `proseWrap: "always"`.
- tsconfig: copy pi-plan-mode's (`strict`, `noEmit`, `moduleResolution: bundler`, bun-types) — proven against jiti-loaded pi extensions.

## 11. Testing and publishing recommendations

- Tests: port upstream's 6 test files (they encode the behavioral contract — budget/abort/settle semantics, watchdog, transcript bounding, sandbox escapes, meta fail-closed, atomic writes) to `bun test` per the template; sandbox tests spawn real Node children, so verify bun compatibility early — if `node:child_process` IPC under bun misbehaves, keep a `node --test` script for the sandbox suite only. Add Effect-level tests using `effect/testing` (TestClock for watchdog/throttle/settle instead of real timers) and one smoke test that `createAgentSession` wiring compiles against the pinned pi version.
- CI gates: `tsc --noEmit`, `oxlint`, `eslint` (max-lines), `oxfmt --check`, `bun test`; plus `wc -l` is redundant once ESLint enforces the budget.
- Publishing: mirror pi-plan-mode — pnpm, `release-please` (node type, bump-minor-pre-major), `files` whitelist excluding `__tests__`, `publishConfig.access: public`, `pi` manifest, `pi-package` keyword, README documenting the `ultracode` trigger, `/workflows`, artifact locations, the Node `--permission` requirement, and the Effect v4 beta pin rationale. Install path for users: `pi install npm:@dreki-gg/pi-workflows`.
